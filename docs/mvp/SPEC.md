# Контур 1 — ТЗ: локальный YAML + рабочий VPN (Mihomo)

## Два контура продукта

1. **Контур 1 (этот документ, делаем сейчас).** Пользователь сам приносит
   YAML-профиль — импортом файла или вставкой текста. Плюс всё, что нужно,
   чтобы с этим профилем реально поднялся VPN: правила маршрутизации
   (приложения/домены), сборка runtime-конфига, `VpnService`, разрешение
   VPN, TUN, интеграция с Mihomo, `protect()`, старт/стоп. То есть контур 1 —
   это полностью рабочий VPN-клиент, где профиль вводится вручную.
2. **Контур 2 (потом, отдельное ТЗ).** Загрузка YAML-профиля с твоего API
   (Config Downloader) и всё, что вокруг этого: обновление профилей,
   привязка к серверному аккаунту и т.п. Контур 2 переиспользует ту же модель
   `ProxyProfile` и весь пайплайн от "есть профиль" до "VPN работает" —
   он просто добавляет ещё один источник профиля, ничего не меняя в контуре 1.

Полная целевая архитектура (оба контура вместе) — [../ARCHITECTURE-FULL.md](../ARCHITECTURE-FULL.md).
Контур 1 — это шаги 2, 4, 6–19 оттуда (без шага 3 — API-загрузки, это контур 2)
и без шага 5 (шифрование хранилища — сознательно отложено, см. ниже).

## ⚠️ Лицензия: Mihomo — GPL-3.0

Выбранная библиотека (`libmihomo-android`, см. ниже) и сам Mihomo
распространяются под **GPL-3.0**. Встраивание её как `.aar` внутрь APK — это
статическое связывание в терминах GPL, а не отдельный процесс/IPC. Это
потенциально означает, что при распространении приложения (публикация в
сторе, передача APK третьим лицам) весь combined work должен соответствовать
условиям GPL-3.0 — то есть, по строгой трактовке, исходный код приложения
тоже должен быть доступен под GPL-совместимой лицензией. Это не блокирует
разработку и тестирование контура 1, но **перед публикацией приложения** этот
вопрос стоит закрыть осознанно (проконсультироваться с юристом либо выбрать
модель распространения, совместимую с GPL). Дальше в этом ТЗ считаем, что
решение принято и мы работаем с `libmihomo-android` как есть.

## Цель контура 1

По завершении: пользователь открывает приложение, импортирует или вставляет
YAML с прокси-сервером, выбирает приложения и добавляет домены, задаёт каждому правилу
режим «С VPN» (PROXY) или «Без VPN» (DIRECT), жмёт START — поднимается VPN.
Трафик маршрутизируется по первому совпавшему правилу: через сервер из YAML
или напрямую. Без совпадений он идёт напрямую. Жмёт STOP — VPN корректно
останавливается.

## В скоупе

### Профиль (локальный ввод)
- Импорт `.yaml`/`.yml` файла через системный file picker.
- Вставка YAML вручную (multiline текстовое поле) как альтернативный способ
  создать профиль.
- Парсинг YAML → `ProxyProfile`.
- Базовая валидация (обязательные поля, понятная ошибка на битом YAML).
- Список сохранённых профилей, выбор активного, удаление.
- Редактирование YAML сохранённого профиля с повторной валидацией.
  ID и активный выбор сохраняются; отмена и ошибка не меняют профиль.
- Хранение на диске (без шифрования — см. "Сознательно отложено").

### Правила маршрутизации
- Отдельный экран приложений устройства (`PackageManager`): название,
  иконка, выбор нужных приложений и взаимоисключающий режим «С VPN» / «Без VPN».
  В правила записывается Android package name, а не отображаемое имя.
- Неотмеченное приложение не имеет собственного правила: для него
  проверяются домены, затем применяется `MATCH,DIRECT`.
- Отдельный экран доменов: ввод/вставка домена в текстовое поле,
  добавление и удаление элементов списка, режим «С VPN» / «Без VPN»
  у каждого домена. Семантика `DOMAIN-SUFFIX`: домен и его поддомены.
- Хранение выбранных пакетов, доменов и их режимов на диске.

### Runtime и VPN
- `RuntimeConfigBuilder`: `ProxyProfile.raw` (весь YAML пользователя,
  см. "Данные") + сгенерированные `rules:` → готовый Mihomo/Clash YAML в
  `cacheDir/mihomo/config.yaml`, создаётся заново при каждом старте,
  удаляется при стопе.
- Подключение `libmihomo-android.aar` в проект (см. "Mihomo — выбранная
  библиотека" ниже).
- `ProxyVpnService`: foreground notification, VPN lifecycle, создание TUN,
  запуск/остановка Mihomo через `Clash.quickSetup`/`Clash.startTUN`.
- Запрос VPN permission (`VpnService.prepare`) перед первым стартом.
- Создание TUN (`VpnService.Builder` → `establish()` → `ParcelFileDescriptor`),
  передача `fd` в `Clash.startTUN`.
- `protect()` для исходящих соединений самого Mihomo (не зациклить трафик) —
  реализуется через `callback`, который принимает `Clash.startTUN` (см. ниже).
- Экран Main: выбранный профиль, количество правил, кнопка START/STOP,
  статус CONNECTED/DISCONNECTED.
- Порядок rules: все правила приложений (`PROXY` и `DIRECT`) → все
  правила доменов (`PROXY` и `DIRECT`) → `MATCH,DIRECT`.
  Первое совпадение определяет маршрут. Явное правило приложения всегда
  приоритетнее доменного: приложение «Без VPN» идёт напрямую даже к домену
  «С VPN», и наоборот.
- Пустой список правил допустим: конфиг содержит только `MATCH,DIRECT`,
  весь трафик идёт напрямую.
- Изменения профиля и правил сохраняются, но применяются только после
  ручного STOP → START. Текущее соединение использует снимок конфигурации
  на момент запуска, без автоматического перезапуска или обновления на лету.
- Ошибка запуска видна на Main; приложение выходит из CONNECTING,
  освобождает ресурсы неудачного запуска и позволяет повторить START.

## Mihomo — выбранная библиотека

`libmihomo-android` ([github.com/oviron/libmihomo-android](https://github.com/oviron/libmihomo-android)) —
упаковывает Mihomo (metacubex/mihomo, форк Clash-Meta) в `libclash.so` на
`arm64-v8a`/`armeabi-v7a`/`x86_64` + готовый Kotlin/JNI фасад. Не нужно писать
свой JNI-мост к Go-коду.

Подключение:

```text
vpn/
  libs/
    libmihomo-android.aar
```

```kotlin
// vpn/build.gradle.kts
dependencies {
    implementation(files("libs/libmihomo-android.aar"))
}
```

API (используется в стадиях H/I из TASKS.md):

```kotlin
// один раз при старте процесса/сервиса
Clash.load(applicationInfo.nativeLibraryDir)

// передать runtime config.yaml, собранный RuntimeConfigBuilder
Clash.quickSetup(
    initParams = """{"homeDir":"${filesDir.absolutePath}"}""",
    setupParams = """{"profile":"${configFile.absolutePath}"}"""
)

// запустить TUN, из ProxyVpnService, после establish()
Clash.startTUN(
    tunFd,      // ParcelFileDescriptor.fd из VpnService.Builder.establish()
    callback,   // сюда же обвязывается VpnService.protect()
    device,
    stack,
    address,
    dns,
    mtu
)

// на STOP
Clash.stopTun()
```

`callback` — тот механизм, которым `protect()` подключается к исходящим
сокетам core (иначе трафик самого Mihomo зациклится обратно в TUN, см.
ARCHITECTURE-FULL.md → раздел 17). Точная сигнатура `callback`/`device`/
`stack`/`address`/`dns` — смотреть в актуальной версии `.aar` при выполнении
задачи H1/H2 в TASKS.md (сигнатура может отличаться между релизами
библиотеки).

## Сознательно отложено (не блокирует контур 1)

- **Шифрование хранилища** (Android Keystore/AES-GCM). Профиль хранится как
  есть в приватной директории приложения (`filesDir`, недоступна другим
  приложениям без root). Добавляется отдельной задачей после того, как
  сквозной VPN-флоу заработает — тогда понятно, что именно шифровать
  (профиль целиком? только пароль?) и не переделывать модель на ходу.
- **Контур 2** — API-загрузка профиля (см. выше).
- `IP-CIDR`/`GEOIP`/`GEOSITE`/`DOMAIN-KEYWORD` правила — только
  `DOMAIN-SUFFIX`.
- Настраиваемый `fallback` — в MVP всегда `MATCH,DIRECT`.
- Несколько одновременно активных профилей / hot-swap сервера без перезапуска
  VPN.

## Данные

### `ProxyProfile`

Ключевое решение: **пользователь приносит весь YAML целиком** (`mode`, `dns`,
`proxies`, `proxy-groups` и т.д.) — **кроме `rules:`**. `rules:` в этом
приложении всегда Android-специфичные (по package name приложений и по
доменам) и всегда генерируются самим приложением из выбора на экранах
Apps/Domains — пользователь их не пишет и не приносит в YAML.

```kotlin
data class ProxyProfile(
    val id: String,          // UUID, генерируется локально при импорте
    val name: String,        // имя профиля — из первого proxies[].name, либо имя файла
    val type: String,        // type первого прокси из proxies[] — для отображения в списке
    val server: String,      // server первого прокси из proxies[] — для отображения в списке
    val port: Int,           // port первого прокси из proxies[] — для отображения в списке
    val raw: String,         // YAML со всеми значениями, БЕЗ ключа rules (если он был — вырезается при импорте)
)
```

`raw` — источник истины для `RuntimeConfigBuilder`: он не пересобирает
`mode`/`dns`/`proxies`/`proxy-groups` из структурированных полей, а берёт
`raw` целиком и дописывает к нему сгенерированный `rules:` (см. G2 в
TASKS.md). Структурированные поля (`name`/`type`/`server`/`port`) существуют
только для списка профилей в UI — на конфигурацию VPN они не влияют.

Если `proxies:` содержит несколько серверов — для отображения (`name`/`type`/
`server`/`port`) в контуре 1 берётся первый элемент списка. Дальше эта
многосерверность не используется: `proxy-groups`/`select` внутри `raw`
решает, какой из них активен, приложение в это не вмешивается.

### Правила

```kotlin
enum class RouteTarget { PROXY, DIRECT }

data class ProxyPackage(val packageName: String, val target: RouteTarget)
data class ProxyDomain(val domain: String, val target: RouteTarget) // DOMAIN-SUFFIX
```

Глобальный набор правил на приложение, не привязан к конкретному профилю.
Для одного package name или домена хранится одно правило; смена режима
обновляет его. Снятие выбора приложения или удаление домена удаляет правило.

### Входной конфиг первого рабочего прохода

Ориентир — предоставленный пользователем полный YAML: `mode: rule`, DNS
в режиме `redir-host`, Shadowsocks (`ss`, `chacha20-ietf-poly1305`) с
`v2ray-plugin`, WebSocket и TLS, группа `PROXY` типа `select` с сервером
и `DIRECT`. Сервер, пароль и остальные параметры пользователь импортирует
сам; реальные credentials в документацию и тестовые данные не копируются.
Для MVP входной конфиг должен содержать `mode: rule` и группу `PROXY`,
на которую ссылаются сгенерированные правила. Параметры подключения
сохраняются при преобразовании YAML. Совместимость выбранной библиотеки
с этим подключением и Android package routing проверяется в первом проходе.

Пример сгенерированных правил (условные приложения и домены):

```yaml
rules:
  - PROCESS-NAME,org.telegram.messenger,PROXY
  - PROCESS-NAME,com.example.app,DIRECT
  - DOMAIN-SUFFIX,example.org,PROXY
  - DOMAIN-SUFFIX,example.net,DIRECT
  - MATCH,DIRECT
```

## Хранение

Без Room (модуль `db` сейчас закомментирован). JSON-файлы в `filesDir` через
`kotlinx.serialization`: `profiles.json`, `proxy_packages.json`,
`proxy_domains.json`. Room/DataStore — можно вернуть позже, если понадобится
реактивность поверх файлов сейчас достаточно `StateFlow` + in-memory кэш,
синхронизируемый с файлом при каждом изменении.

## Модули

- `feature-selfprofile` — экраны профилей, импорт/вставка YAML, парсинг,
  хранение профиля. Для `impl` используется
  `ghostytrafficrider.android.feature`, для `api` —
  `ghostytrafficrider.android.feature.api`.
- `feature-routing` — экраны приложений/доменов, хранение правил.
  Те же convention-плагины для `api` и `impl`.
- `vpn` (обычный `android.library`, без Compose) — `RuntimeConfigBuilder`,
  `ProxyVpnService`, `libmihomo-android.aar` (см. "Mihomo — выбранная
  библиотека"), работа с `PackageManager` для списка приложений может жить
  здесь или в `feature-routing` — решить в задаче на Apps-экран (см.
  TASKS.md), т.к. `feature-routing` и так его использует.

Каждая фича сразу разделена на `api` и `impl`:
- `:feature-selfprofile:api`, `:feature-routing:api` — публичные модели и контракты.
- `:feature-selfprofile:impl`, `:feature-routing:impl` — UI, парсинг, хранение и DI.
  Реализация зависит от своего `api`; классы реализации объявляются `internal`.
- Другие фичи и `vpn` используют только `api`; `app` подключает `impl` для DI.
  Публичная точка сборки Koin-модуля — единственное инфраструктурное исключение.

Правила и шаблон создания модулей: [../MODULES.md](../MODULES.md).
Общие плагины и зависимости берутся из convention-плагинов в `build-logic`.
В `impl` явно добавляется зависимость от своего `api`; остальные зависимости
добавляются только если их ещё не предоставляет convention-плагин.

## Как это ложится на текущую структуру проекта

Проект уже multi-module (`build-logic` + `:app` + `:framework` +
`:framework:tools` + `:framework:router`), новые модули встраиваются в неё,
а не строятся с нуля:

- `feature-selfprofile:impl` и `feature-routing:impl` зависят от `:framework`,
  `:framework:tools`, `:framework:router` так же, как сейчас `:app`
  (`implementation(project(":framework"))` и т.д. — см. `app/build.gradle.kts`).
- Каждый экран регистрирует свои destinations через `Router.Provider`,
  привязанный в Koin-модуле фичи (`bind Router.Provider::class`) — так же,
  как `RouterModule` в `:app` регистрирует сам `Router`. `MainActivity` уже
  собирает все `Router.Provider` из Koin (`getKoin().getAll<Router.Provider>()`)
  в `entryProvider`, новым фичам не нужно ничего менять в `MainActivity`.
- ViewModel'и экранов наследуются от `BaseViewModel<State>` из `:framework`
  (`UiState`/`UiEvent`/`UiStatus`), а не пишутся с нуля — паттерн уже есть.
- Переходы между экранами — через `navTransitionMetadata`/`NavTransition` из
  `:framework:router`, как в `RouterModule.enterContentTransform`/
  `popContentTransform` в `:app`.
- Для MVP строки разрешено задавать прямо в Compose и Kotlin-коде,
  без переноса в `strings.xml`. Иконки — из уже подключённого Material Icons.
- Цвета/типографика/отступы/скругления — уже готовы в `:framework/theme`
  (`AppTheme`, `AppColors`, `AppTypography`, `AppPaddings`, `AppCorners`).
  Новые экраны используют `AppTheme.color`, `AppTheme.typography`,
  `AppTheme.padding`, `AppTheme.corner` — свою палитру или типографику не
  придумываем, единообразие с остальным приложением бесплатное.
- **Автообнаружение модулей уже настроено**: `settings.gradle.kts` сканирует
  каталоги на верхнем уровне и подключает любой с `build.gradle.kts` —
  создать `feature-*/api/build.gradle.kts` и `feature-*/impl/build.gradle.kts`
  достаточно, чтобы Gradle их увидел, без правок `settings.gradle.kts`.
- **`app/build.gradle.kts` тоже не нужно трогать для `feature-*`** —
  `implementationFeatureModules()` уже подключает подмодули `api`/`impl`
  каталогов `feature-*` автоматически. Для `vpn` это правило не действует (не матчит
  `feature-*` префикс) — его нужно добавить в `dependencies {}` в
  `app/build.gradle.kts` вручную, одной строкой
  (`implementation(project(":vpn"))`), когда дойдём до задачи с
  `ProxyVpnService`.
- `AndroidManifest.xml` для `:app` потребует правки только на задаче с
  `ProxyVpnService` (регистрация `<service>` с `BIND_VPN_SERVICE` и
  `<intent-filter>` для `android.net.VpnService`) — сейчас (профиль/правила)
  манифест не трогаем.

## Новая зависимость: YAML-парсер

Используется `org.snakeyaml:snakeyaml-engine:2.9` в `feature-selfprofile:impl`.
Первоначальный кандидат `kaml` архивирован автором. SnakeYAML Engine
разбирает YAML в map/list и записывает его обратно после удаления `rules`.
Значения остальных ключей сохраняются; форматирование и комментарии — нет.
Парсер проверяет обязательные поля первого прокси, диапазон порта,
`mode: rule` и группу `PROXY`. Синтаксические ошибки возвращаются без
исходного текста YAML. Проверку параметров конкретного протокола выполняет
Mihomo при старте; её результат должен отображаться в UI.

## Критерии готовности контура 1

- Импорт `.yaml` файла (полный Mihomo-конфиг без `rules:`) с одним
  прокси-профилем → профиль в списке с верным именем/типом/сервером.
- Вставка того же YAML текстом → тот же результат.
- Битый YAML → понятная ошибка, ничего не падает.
- Список приложений: отмеченные пакеты сохраняются между перезапусками.
- Список доменов: добавление/удаление сохраняется между перезапусками.
- Профили/пакеты/домены переживают перезапуск процесса.
- START с выбранным профилем → запрашивается VPN permission (если не
  выдано) → поднимается VPN. Правила «С VPN» дают PROXY, «Без VPN» — DIRECT.
- Проверены оба конфликта: приложение DIRECT + домен PROXY и приложение
  PROXY + домен DIRECT; в обоих случаях побеждает приложение.
- Для приложения без правила действуют доменные правила; без совпадений
  трафик идёт напрямую. При пустых правилах весь трафик идёт напрямую.
- Выбор режимов приложений и доменов сохраняется между перезапусками.
- Изменения профиля/правил при активном VPN не меняют текущее подключение;
  после STOP → START применяются сохранённые изменения.
- Ошибка старта отображается на Main, CONNECTING не зависает, ресурсы
  очищаются, повторный START доступен.
- STOP → VPN корректно останавливается, `cacheDir/mihomo/config.yaml`
  удаляется, foreground-уведомление исчезает.
- Повторные START/STOP не оставляют висящих процессов/сокетов/уведомлений.
